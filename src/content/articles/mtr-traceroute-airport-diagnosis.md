[机场测速怎么做](/tutorials/how-to-test-airport-speed/)介绍的是测下载、上传速度和延迟数字本身。但有时候你更想知道的是：延迟高、丢包多，到底是出在自己家里的网络、运营商出口，还是中间的中转线路？这时候单测一个延迟数字不够用，需要用到逐跳诊断工具——最常见的是 MTR（My Traceroute）。

## MTR 是什么，和普通 ping、traceroute 有什么区别

传统的 traceroute 只告诉你数据包经过了哪些中间节点（跳数），ping 只告诉你到某一个目标的延迟和丢包。MTR 把两者结合起来：它会持续、重复地对路径上的每一跳分别发包，统计每一跳各自的延迟和丢包率，最终给出一张"路径上每一站分别怎样"的表格，而不是只有起点和终点两个数字。这让你有机会判断问题大致出在路径的哪一段，而不只是知道"终点丢包了"这个结果。

## 怎么运行 MTR

不同系统上的工具名字和获取方式不同，这里只做概念性介绍，具体操作以你所用系统的官方文档或软件说明为准：

- **Windows**：系统自带的是 tracert，功能比较基础；如果需要逐跳的延迟和丢包统计，通常会用第三方的 WinMTR 一类工具
- **macOS / Linux**：大多数发行版可以直接安装 mtr 命令行工具，终端里输入 `mtr 目标地址` 即可开始持续测试
- **手机端**：部分网络工具 App 提供类似功能，但功能和细节通常不如电脑端完整，建议优先用电脑测试

测试目标建议选你平时访问、节点連接的目标地址或者公开的测速服务器，持续运行几分钟，尽量覆盖到你怀疑有问题的时间段（比如晚高峰）。

## 怎么读懂 MTR 的结果

MTR 结果通常会按跳数列出每一跳的地址、丢包率、平均延迟等数据。看结果时注意几点：

1. **只看中间某一跳丢包，不代表真的丢包**：很多网络设备对 ICMP（也就是 ping、MTR 依赖的协议）有限速或者优先级降级策略，会让中间某一跳显示丢包，但实际业务流量（网页、视频）并没有受影响。这是 MTR 结果里最容易被误读的地方。
2. **重点看最后一跳（目标）的数据**：相比中间某一跳孤立的丢包，最终到达目标的丢包率和延迟更能反映你实际能感知到的体验。
3. **去程和回程路径可能不同**：你这边测出来的路径，不代表数据返回时走的是完全相同的路径，这也是为什么有时候"看起来是某一跳的问题"但实际定位后发现并非如此。
4. **单次结果仅供参考**：和普通测速一样，网络路径和负载会随时间变化，建议多测几次、覆盖不同时段，而不是只看一次结果下结论。

## 常见结果模式和大致方向

| 观察到的现象 | 大致可能方向 |
| --- | --- |
| 前几跳（家庭路由器、本地运营商出口附近）就出现较高丢包，且最终目标也丢包 | 优先怀疑本地网络或所在地区运营商线路，可以换网络环境再测一次 |
| 前面各跳都正常，但到最后一跳（目标）才出现丢包或延迟明显升高 | 可能是目标节点本身或中转/落地段的问题，可以先换节点测试排除 |
| 某个中间跳单独显示高丢包，但再往后的跳和最终目标都正常 | 大概率是该设备对 ICMP 限速导致的误读，不代表实际业务流量受影响，可以不用特别担心 |
| 所有跳的数据都正常，但应用里仍然感觉卡顿 | 问题可能不在网络路径本身，建议转向检查客户端配置，参考[机场连接不上怎么办？从订阅、节点到客户端逐步排查](/troubleshooting/connection-troubleshooting-step-by-step/) |

这张表格列的是一般性的排查思路，不是固定结论，具体情况还要结合你自己的测试结果判断。

## 什么情况下适合用 MTR

MTR 不是日常必须用的工具，更适合以下几种场景：

- **怀疑丢包或延迟异常，但又想确认具体是哪一段的问题，而不只是"感觉卡"**
- **需要向服务商客服说明问题时，提供比"我感觉很卡"更具体的材料**
- **换了节点、换了本地网络之后，想对比两次路径表现有没有实质差异**
- **长期反复出现同一类问题，想确认是不是固定发生在路径上的同一段**

如果只是偶尔一次网页打不开、刷新一下就好了，通常不需要专门跑一次 MTR，先按[连不上机场代理？常见连接失败排查步骤](/troubleshooting/connection-failed-troubleshooting/)里的基础检查走一遍就够了。

## 自己怎么验证测试结果靠不靠谱

跑完一次 MTR，建议按下面几点自己核对一遍，避免被单次结果误导：

1. **换一个时间段再测一次**，看现象是否重复出现，而不是偶然一次的波动
2. **换一个目标地址再测一次**，排除是不是目标服务器本身的问题，而不是路径问题
3. **如果条件允许，换一个节点测同样的目标**，对比两次路径和丢包表现是否有明显差异
4. **把测试时的时间、节点、目标地址都记下来**，方便之后对比或者反馈给客服

只有在多次测试都指向同一个方向时，才比较适合下结论，单次结果更多是起点，不是终点。

## 和其他排查方式配合使用

MTR 定位的是"路径上哪一段可能有问题"，具体丢包率、延迟数字该怎么判断是否正常，可以参考[机场丢包率多少算高](/knowledge/airport-packet-loss-explained/)和[机场延迟多少算正常](/knowledge/airport-latency-normal-range/)；如果怀疑是机场本身晚高峰拥堵之类的结构性原因，可以看[机场为什么会不稳定](/knowledge/why-airport-is-unstable/)背后的常见机制说明。

## 常见问题

**MTR 显示某一跳丢包很高，是不是说明这个机场有问题？**
不一定。很多路由设备对 ICMP 探测包本身做限速，会让中间跳看起来丢包很高，但实际转发业务流量时并不受影响。更可靠的判断依据是最终目标跳的数据，以及你自己实际使用时的体验。

**要测多久才算够？**
没有固定标准，建议至少持续运行几分钟，并且尽量覆盖到你怀疑有问题的时间段（比如晚高峰），单次几秒钟的结果偶然性比较大。

**MTR 结果能不能直接拿去找客服证明是机场的问题？**
可以作为参考材料之一，但建议同时说明测试的时间、节点和网络环境，客服通常还需要结合自己后台的数据一起判断，MTR 结果本身不是绝对结论。

**手机上有没有办法测？**
部分网络诊断类 App 提供类似功能，但功能完整度通常不如电脑端的专门工具，如果条件允许，建议优先用电脑测试。
