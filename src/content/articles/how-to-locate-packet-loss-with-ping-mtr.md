[机场测速怎么做](/tutorials/how-to-test-airport-speed/)介绍的是怎么测下载速度和延迟数字，但测出来的数字只能告诉你"有没有问题"，不能告诉你"问题大致出在哪一段"。这篇文章介绍几个免费的命令行工具，帮助你初步判断丢包和延迟发生在本机网络、运营商线路，还是更靠后的节点环节。

## 为什么只测速度不够

一次测速结果如果不理想，可能的原因有很多：你自己的 Wi-Fi 信号不好、本地运营商出口拥堵、跨境线路临时波动、机场节点当前负载高，或者单纯是目标网站响应慢。单看一个下载速度数字，没办法区分这些可能性。Ping、Traceroute、MTR 这几个工具能看到数据包经过的路径和每一跳的表现，可以帮你把范围缩小一些，而不是只能靠猜。

## 用 Ping 看本机到目标是否稳定

Ping 是最基础的工具，发送一连串小数据包到目标地址，记录每次的往返时间和是否超时。

- Windows：命令提示符里输入 `ping -t 目标地址`，持续发送直到手动停止（Ctrl+C）
- macOS / Linux：终端输入 `ping 目标地址`，默认会持续发送

重点看两部分：每一行的 `time=` 数值（延迟是否稳定、有没有明显跳动），以及停止后汇总的丢包统计（显示丢了百分之多少的包）。如果连 Ping 都大量丢包，说明问题可能出现得比较早，不一定是机场节点本身的问题。

## 用 Traceroute / Tracert 看经过了哪些中间环节

Traceroute（macOS/Linux 下是 `traceroute 目标地址`，Windows 下是 `tracert 目标地址`）会列出数据包从你的设备到目标地址，中间经过的每一个路由节点，以及到达每一跳所用的时间。

看这份列表时，重点关注：延迟是不是从某一跳开始突然大幅上升——这通常意味着问题出现在那一跳之后的路径上，比如跨境出口、某个运营商的中转环节。如果延迟一路平稳上升到终点，没有某一跳突然跳变，说明路径本身相对正常。

## 用 MTR 看每一跳的持续丢包率

Traceroute 只测一次，参考价值有限；MTR（My Traceroute）会对路径上每一跳持续发送多次探测包，统计每一跳各自的丢包率，参考价值更高。

- macOS：可以用 Homebrew 安装（`brew install mtr`）
- Linux：多数发行版可以直接用包管理器安装（比如 `apt install mtr`）
- Windows：可以使用 WinMTR 这类图形化替代工具，功能类似

运行后持续观察一两分钟，重点看 `Loss%` 这一列：如果只是中间某一跳单独显示丢包、但后面的跳数丢包率又恢复正常，这种情况通常不代表真实丢包（下面会解释原因）；如果丢包从某一跳开始一直持续到终点，才比较值得关注。

## 看懂输出时的几个前提

- **中间某一跳单独丢包不一定是真丢包**：很多路由设备会限制处理 ICMP（Ping 类探测包）的优先级，即使正常转发数据也可能"不理会"探测包，导致 Traceroute/MTR 里单独某一跳显示丢包，但这一跳之后的所有跳数都正常——这种情况通常可以忽略，重点看丢包是否从某一跳开始持续到终点。
- **只反映一个方向**：这些工具测的是你到目标这个方向的路径，不代表返回路径完全一样，网络上去和回来走的路线有时并不对称。
- **单次结果同样有偶然性**：和测速一样，建议在不同时段（尤其是晚高峰）各测一次，结合[机场测速结果为什么每天不一样](/knowledge/why-speed-test-varies-daily/)里提到的影响因素一起判断，而不是只跑一次就下结论。

## 大致怎么判断问题出在哪一段

- 如果从最初几跳（通常是你的路由器、本地运营商网关）就开始丢包或延迟明显偏高，大概率是本地网络或本地运营商接入的问题，建议先排除 Wi-Fi 信号、路由器负载等本地因素
- 如果延迟从某个明显是跨境或跨运营商的中间跳数开始大幅上升，但之前和之后都相对正常，说明问题更可能出现在这段跨境线路上
- 如果只有最后一两跳（接近目标地址）持续丢包或延迟偏高，问题更可能出在落地节点或目标服务器本身，而不是你本地或中间线路

这只是大致的判断思路，不是精确诊断——具体数值怎么解读，仍然要结合[机场丢包率多少算高](/knowledge/airport-packet-loss-explained/)和[机场延迟多少算正常](/knowledge/airport-latency-normal-range/)里的参考区间一起看。

## 排查完之后能做什么

如果判断问题出在本地网络，先按常规思路排除 Wi-Fi、路由器、其他设备占用带宽等因素；如果怀疑是客户端配置或订阅层面的问题，可以换个角度参考[机场连接不上怎么办？从订阅、节点到客户端逐步排查](/troubleshooting/connection-troubleshooting-step-by-step/)。如果用 MTR 记录确认问题持续出现在机场侧，带着这份记录（哪一跳开始丢包、丢包率多少、测试时间段）联系服务商客服，通常比只说"连不上"或"很卡"更容易被准确定位和处理。

## 常见问题

**普通用户有必要学会用 MTR 吗？**
不是必须的。如果只是偶尔卡顿、换个节点就能解决，不需要深入到这一步；但如果问题反复出现、换节点和换时段都解决不了，用 MTR 记录一段数据，能让排查和沟通都更有效率。

**Traceroute 和 MTR 都显示正常，但实际使用还是很卡，怎么办？**
这两个工具测的是网络路径本身是否畅通，不代表应用层的表现（比如目标网站本身响应慢、客户端协议配置不合适）。可以先确认是不是特定网站或特定协议的问题，再按分层思路继续排查。

**手机上能用这些工具吗？**
Ping 和 Traceroute 在部分手机 App（支持网络诊断功能的工具类 App）里可以用，但 MTR 这类工具通常需要在电脑上运行，如果主要在手机上使用机场代理，建议遇到问题时换到电脑上做一次更完整的排查。
