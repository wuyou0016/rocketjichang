知道"丢包率偏高"只是第一步，想进一步判断问题出在自己的本地网络、中间路由，还是机场节点本身，需要用到路由追踪类工具。这篇文章介绍怎么用 MTR、traceroute 这类工具自己动手排查，不涉及具体某个机场节点的实测数据。

## 为什么只看丢包率数字不够

[机场丢包率多少算高](/knowledge/airport-packet-loss-explained/)讲过怎么理解丢包率的数值区间，但一个笼统的丢包率数字，并不能告诉你问题出在哪一段链路——是你自己的路由器、本地运营商的出口，中间经过的某一跳，还是机场节点本身。如果不知道问题出在哪一段，换节点、换协议这类操作很可能是在盲目尝试。路由追踪工具的作用，就是把"从你的设备到目标服务器"这条路径拆成一跳一跳来看，逐段定位。

## MTR 是什么，和 ping、traceroute 有什么关系

- **ping** 只测试你和目标地址之间端到端的延迟和丢包，看不到中间经过了哪些节点
- **traceroute（Windows 下是 tracert）** 能显示数据包经过的每一跳路由，但通常只发送少量探测包，偶然性较大
- **MTR（My Traceroute）** 相当于把 ping 和 traceroute 结合起来，持续对路径上的每一跳发送探测包，既能看到完整路径，又能看到每一跳各自的延迟和丢包统计，样本量更大，参考价值也更高

如果只是想快速看一眼路径，traceroute 已经够用；如果想判断丢包具体发生在哪一跳，MTR 是更合适的工具。

## 怎么在自己电脑上运行

不同系统下获取路径信息的命令略有不同，具体参数以你使用的系统版本为准：

- **Windows**：可以用系统自带的 `tracert 目标地址` 看路径，或者用 `pathping 目标地址` 获得类似 MTR 的持续统计效果，pathping 运行时间较长，需要耐心等待
- **macOS / Linux**：系统通常自带 `traceroute` 命令；MTR 工具本身在 macOS 上可以通过包管理工具安装，Linux 发行版大多可以直接通过软件包管理器安装
- **手机**：应用商店里有一些图形化的网络诊断类 App，功能上大多是对 traceroute / ping 的封装，操作逻辑和电脑上类似

目标地址可以选你日常访问的服务域名，也可以选节点地址本身，具体测哪个取决于你想排查的是"到目标网站"还是"到节点入口"这一段。

## 怎么读懂 MTR 的结果

MTR 的输出通常是一张表格，每一行代表路径上的一跳，主要看这几列：

| 列名 | 含义 |
| --- | --- |
| Loss% | 这一跳的丢包率 |
| Snt | 已发送的探测包数量，数量越多参考价值越高 |
| Avg | 平均延迟 |
| Best / Wrst | 最好和最差的一次延迟 |
| StDev | 延迟的标准差，数值越大说明这一跳延迟波动越大 |

举个示例（数字仅用于说明表格怎么看，不代表任何真实测试结果）：如果第 3 跳开始 Loss% 持续显示较高的数值，并且这个丢包一直延续到最后一跳，通常说明问题出在第 3 跳所在的这一段链路；如果只有中间某一跳单独显示丢包，而这一跳之后的所有跳又恢复正常（Loss% 归零），这种情况更可能是下面要讲的"假丢包"，不一定代表真实的传输问题。

## 常见误判：ICMP 限速导致的"假丢包"

这是自己动手排查时最容易踩的坑：很多路由器和网络设备出于安全和负载考虑，会对 ICMP 协议（ping、traceroute、MTR 都依赖这个协议）的响应做限速或者干脆不响应。这会导致某一跳单独显示很高的丢包率，但这一跳之后的所有跳都恢复正常。

判断是否是假丢包，可以看这一跳之后的路径表现：

- 只有中间某一跳丢包，之后各跳都正常 → 大概率是那一跳设备限制了 ICMP 响应，不代表真实丢包，可以忽略
- 从某一跳开始丢包，并且之后所有跳都跟着丢包 → 更可能是真实的传输问题，问题出在这一跳或者这一跳之前的链路上
- 只有最后一跳（也就是目标本身）丢包，其余全部正常 → 问题更可能出在目标服务器自身，或者是目标服务器同样限制了 ICMP 响应，需要结合实际访问体验综合判断

## 结合机场场景理解路径分段

机场代理的完整路径大致可以分为几段：你的设备到本地出口、本地出口到节点入口、节点内部处理、节点出口到目标网站。[什么是中转线路](/knowledge/what-is-transit-route/)里介绍过直连、中转、专线在链路结构上的区别，这里的路径追踪思路是一致的——MTR 能帮你判断，如果丢包发生在到达节点入口之前，问题大概率和机场本身无关，是你自己的本地网络或者运营商出口的问题；如果丢包发生在节点入口之后，才需要考虑是不是节点或者线路本身的问题。这类不稳定的具体成因，也可以参考[机场为什么会不稳定](/knowledge/why-airport-is-unstable/)。

## 测试时的注意事项

- 单次测试受偶然因素影响较大，建议连续测试几次，并覆盖白天和晚高峰（通常指 20:00-23:00 前后）两个时段
- 记录测试用的目标地址、时间段和路径截图，方便之后对比，或者向客服反馈问题时提供依据
- 想快速计算一组 ping 结果里的丢包率、延迟分布，可以用本站的[延迟丢包计算器](/tools/latency-loss/)，直接粘贴 ping 输出即可得到统计结果，同样只在浏览器本地计算，不会上传数据
- 路径追踪工具能帮你定位问题大致出在哪一段，但不能替代和客服的沟通——如果最终判断问题出在节点内部或者机场出口，仍然需要联系服务商确认

## 常见问题

**MTR 显示某一跳丢包很严重，是不是这个机场有问题？**
不一定。如果这一跳之后的所有跳都恢复正常，很可能是那台设备限制了 ICMP 响应造成的"假丢包"，不代表真实的传输质量问题，需要结合后续跳的表现综合判断。

**用节点地址测和用目标网站域名测，结果会不一样吗？**
会。测节点地址主要反映"你到节点入口"这一段的情况；测目标网站域名反映的是完整路径，包含节点到目标网站这一段。想分别定位问题，两者都测一下会更清楚。

**手机上能做类似的路径追踪吗？**
可以，应用商店里有一些网络诊断类工具提供类似功能，原理和电脑上的 traceroute、MTR 是一致的，只是界面更简化。

**追踪结果显示路径正常，但实际使用还是很卡，是为什么？**
路径追踪主要反映延迟和丢包这两个指标，实际卡顿也可能和带宽、目标服务器负载、DNS 解析等其他因素有关，可以结合[机场速度怎么看](/knowledge/airport-speed-explained/)一起排查。

**要不要每次卡顿都做一次 MTR？**
没必要。偶尔卡顿先按常规思路排查即可，MTR 更适合在问题反复出现、需要向客服说明具体情况，或者自己想深入了解问题出在哪一段时使用。
